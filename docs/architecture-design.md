# 可选项目架构设计

只有需要明确架构方向、讨论关键取舍或查看架构图时才使用Architecture Copilot。普通功能开发直接按分层文档实现与测试，不要求先设计架构。已确定的设计保持稳定，普通更新不重画；显式架构修订才形成新基线。设计基线确认不是开发后的验收。

在原宿主会话加载同一Architecture Copilot Skill：源码现状模式先读证据再保存来源图，不要求草案；设计模式只保存已明确发起的草案。Skill不可用时停止，不回退旧提示词。浏览器不发起或切换模型会话。

## 开始设计

1. 在原AI CLI/应用明确设计范围，调用 `architecture_design_begin` 发起草案；修订需说明理由。
2. Agent按Skill设计模式读取草案和必要参考，携带当前版本/草案ID保存proposal，沿用原模型、思考和历史。
3. 浏览器刷新后只读查看正文、ASCII、画板与差异；既有确认版本仍可选择查看。
4. 网页不再提供开始、保存、确认或放弃按钮；也不新增Agent/MCP自行确认权限。当前草案不应被表述成已确认基线。

设计写入需活动STATE任务和明确授权；Skill由宿主按需提供。模型权限/费用仍由原宿主管理，浏览器不列模型、不发提示词、不停止聊天，也不自动轮询/重发。

## 稳定基线与显式修订

### AD-001 — 确认前只是草案

原宿主首次创建草案不产生确认基线。Agent保存方案后仍只是草案；浏览器只读展示，不自动确认。既有确认记录继续绑定原内容和版本。正文以纯文本展示，不执行文档HTML或命令。

### AD-002 — 普通更新不改变基线

默认显示已有当前基线。普通刷新、工作项更新、源码变化与源码重分析不替换设计。需要修订时在原宿主显式发起并说明理由；旧基线保持可见，草案单独显示。既有版本可从选择器查看，读取不改历史。

### AD-003 — 项目和任务之间不串用确认

设计绑定工作区、STATE、独立草案ID和设计记录。过期版本或其它任务的草案不能被新写入复用。切换项目关闭旧详情，迟到读取不能覆盖新项目；旧会话不能将迟到结果写入重新创建的草案。旧任务草案不自动改绑。

### AD-004 — ASCII为准，再转换画板

正文受管ASCII区块是结构的权威：方框的稳定ID/标题确定节点，`[from] -- 标签 --> [to]`确定有向关系；画板只显示解析结果。修改ASCII后保存，即使旧nodes/edges未同步，也以ASCII更新结构，不再反向覆盖文本。nodes仅补充同ID的职责说明/安全文件路径；新增ID缺少说明时以标题补充，files为空。

只解析固定语法：`Nodes v2`下依次列四行方框（`+---+`、`| [id] |`、`| 标题 |`、边框），再以`Relationships`列箭头，无关系写`(none)`。控制字符、反引号、尖括号和反斜线用`\uXXXX`转义；不推测任意手绘布局。重复ID、未知端点、无效语法/超限均拒绝，保留原记录。空白/框宽可规范化，但不改节点和关系。

区块用governance:architecture-ascii:start/end标记及text围栏包裹，只能有一份完整区块。旧`Nodes`语法仍可读；没有区块的旧记录只读生成ASCII再转换，不改文件/确认指纹。兼容旧调用时首次由nodes/edges初始化区块；此后编辑ASCII。切换版本使用各版ASCII；确认基线仍需人工审阅，不能直接修改已确认记录。

关联检查只证明列出的隔离浏览器场景，不代表真实宿主、模型对话质量或整个设计的正确性。见 [文档驱动开发](doc-driven.md)。

## 设计不是源码现状

- 「设计方案」表达计划、决定、代价与限制；节点可以没有源码文件。
- 「源码现状」仍来自显式选定的源码和指纹，两份图不互相覆盖。
- 确认设计不是批准代码实施，也不是测试通过；STATE仍决定实施范围，行为证据仍来自实际检查。
- 确认记录是调用方声明，不认证审阅人身份；提示约束不是沙箱，外部工具仍可能直接修改文件。

## 数据与接口

独立数据保存在 `.governance/architecture-design.json`，包含当前草案和追加的确认历史。读取缺省项目不创建文件；损坏记录保留并报错，不能覆盖“恢复默认”。

Agent工具仍只开放 `architecture_design_snapshot`、`architecture_design_begin`、`architecture_design_save`；保存需明确发起草案，携带expectedRevision及expectedDraft。浏览器仅允许snapshot，已撤下确认/放弃入口；未新增Agent/MCP确认动作，不能自行宣称基线已确认。底层原确认守卫与历史兼容保留。配置见[MCP与Skill](mcp.md)。

proposal包含title、可读document、nodes和edges；每节点id/title/description/files，关系from/to/label。通常3–5个核心职责，一张图一个层级，箭头说明实际设计含义。files可为空，不要求未来代码已经存在，不代表源码验证。

最多40节点、100关系、60路径；正文含生成ASCII总计20000字符，超限拒绝而不截掉模块。保留最多20个确认版本、单文件1MiB；本版本不自动裁剪/归档历史。
